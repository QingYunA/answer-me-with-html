Git merge vs git rebase

Both integrate changes from one branch into another. They differ in what they do to your commit history.

The starting point

Say main moved on after you created feature. The two branches have diverged from a common ancestor B.

Arrows point to parents. E's parent is B; E and F are your work.

git merge

git switch main
git merge feature

Merge creates a new merge commit (M) with two parents: the tips of both branches. Existing commits are untouched, and the true shape of history, including the fact that work happened in parallel, is preserved.

M has parents D and F. E and F keep their original hashes.

  • History: non-destructive, but becomes a graph with many merge commits and crossing lines.
  • Conflicts: resolved once, in the merge commit.
  • Fast-forward: if main hasn't moved, git just slides the pointer forward and creates no merge commit (use --no-ff to force one).

git rebase

git switch feature
git rebase main

Rebase takes your commits (E, F), and replays them one by one on top of the new base (D). Each replayed commit has a new parent, so it gets a new hash: E′ and F′. The originals become unreferenced (still reachable via git reflog for a while).

History is now a straight line. E′ and F′ have the same changes as E and F but different hashes.

To finish, fast-forward main: git switch main && git merge feature. No merge commit is needed.

  • History: rewritten and linear; easy to read and bisect.
  • Conflicts: may need resolving once per replayed commit.
  • Side effect: the record of when and how the work actually branched is lost.

The golden rule

Never rebase commits that others have already pulled. Rebasing rewrites hashes; teammates holding the old commits will see duplicated or diverging history. Rebase your own local or private branches; merge for shared ones. If you must push a rebased branch, use git push --force-with-lease.

Rules of thumb

Use merge when…
  • integrating a finished feature into a shared branch
  • you want a faithful record of what happened
  • the branch is public
Use rebase when…
  • updating your private feature branch with the latest main
  • cleaning up commits (git rebase -i)
  • you want a linear history

A common workflow: rebase your feature branch onto main while you work, then merge it (possibly with --no-ff) when it's done.
