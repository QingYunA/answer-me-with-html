TCP Connection Lifecycle

The three-way handshake and the four-way teardown

Why TCP needs these exchanges

TCP is a reliable, ordered, connection-oriented byte stream. Before data flows, both ends must agree they are willing to talk and must exchange initial sequence numbers (ISNs), which let each side number bytes, detect loss and reorder segments. When finished, each direction of the stream is closed independently so no in-flight data is lost.

The relevant header flags are SYN (synchronize sequence numbers), ACK (acknowledgment field is valid), FIN (sender has no more data) and RST (abort).

1. Three-way handshake (connection setup)

StepDirectionSegmentMeaning
1Client → ServerSYN, seq = x"I want to connect; my ISN is x." Client enters SYN_SENT.
2Server → ClientSYN+ACK, seq = y, ack = x+1"Got it; here is my ISN y." Server enters SYN_RCVD.
3Client → ServerACK, ack = y+1"Got yours too." Both sides are ESTABLISHED; data may already ride on this segment.

Why three and not two?

Each side must prove it can both send and receive, and each ISN must be acknowledged. Two messages would leave the server unsure the client received its ISN, and would let stale duplicate SYNs from old connections create phantom half-open connections. The third segment confirms the client's view is current.

Practical notes: a SYN consumes one sequence number, which is why the ACK is x+1. Servers defend against SYN floods with SYN cookies. Options such as MSS, window scaling, SACK and timestamps are negotiated in the SYN and SYN-ACK. TCP Fast Open can carry data in the SYN on repeat connections.

2. Four-way teardown (connection close)

TCP is full-duplex: each direction is a separate stream and is closed on its own with a FIN. That is why closing usually takes four segments. After one side sends FIN, it can still receive data (a "half-close").

StepDirectionSegmentMeaning
1Active → PassiveFIN"I have no more data to send." Enters FIN_WAIT_1.
2Passive → ActiveACKAcknowledges the FIN. Passive side is in CLOSE_WAIT; active side moves to FIN_WAIT_2.
3Passive → ActiveFINOnce the application finishes and calls close(), the passive side sends its own FIN and enters LAST_ACK.
4Active → PassiveACKFinal acknowledgment. Active side enters TIME_WAIT; passive side goes straight to CLOSED.

TIME_WAIT

The side that closes first lingers in TIME_WAIT for 2×MSL (maximum segment lifetime; commonly 60 seconds total on Linux). This ensures that (a) the last ACK can be retransmitted if it was lost, since the peer would resend its FIN, and (b) delayed segments from the old connection expire so they cannot corrupt a new connection reusing the same 4-tuple.

Variations: if the passive side has nothing left to send, it may combine its ACK and FIN into one segment, making a "three-way" close. If both sides send FIN simultaneously, they pass through CLOSING to TIME_WAIT. An RST aborts a connection immediately without this graceful exchange.
