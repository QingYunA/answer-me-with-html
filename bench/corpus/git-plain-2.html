git merge vs git rebase

Both commands integrate changes from one branch into another. They produce the same final content when conflicts are resolved the same way, but they record very different history.

Starting point

You branched feature off main at commit B. Since then, main gained D and E, and feature gained C and F.

(Orange = feature commits, blue/grey = main. Arrows point to parents.)

git merge

git switch main
git merge feature

Creates a new merge commit M with two parents: the tip of main and the tip of feature. Existing commits are untouched.

  • History is non-linear but truthful: it shows the work happened in parallel.
  • No commit is rewritten; commit hashes stay the same.
  • Safe on shared branches.
  • Conflicts are resolved once, in the merge commit.
  • If main hasn't moved, git does a fast-forward (no merge commit) unless you pass --no-ff.

git rebase

git switch feature
git rebase main

Finds the commits unique to feature (C, F), and replays them one by one on top of main's tip, creating new commits C′ and F′. The originals become unreferenced (still in the reflog for a while).

  • History becomes linear, as if you started work from the latest main.
  • Commits are rewritten: new parents mean new hashes.
  • Conflicts may need resolving once per replayed commit.
  • Afterwards, merging feature into main is a clean fast-forward.

When to use which

  • Rebase your own local, unpublished branch to pick up the latest main and tidy it (git rebase -i to squash/reorder) before opening a PR.
  • Merge to integrate finished work into shared branches, or whenever preserving the true history matters.
  • Many teams combine them: rebase while developing, merge (or squash-merge) to land.

Golden rule: never rebase commits that others have already based work on (public/shared branches). Rewriting them forces collaborators to reconcile diverging histories. If you must update a rebased branch you own, use git push --force-with-lease.
