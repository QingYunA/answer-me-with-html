git merge vs git rebase

Both commands integrate changes from one branch into another. They differ in what they do to your commit history: merge preserves it, rebase rewrites it.

The starting point

You branched feature off main. Since then, both branches gained new commits, so they have diverged.

main commitsfeature commitsnewly created commits

git merge

git switch main
git merge feature

Git finds the common ancestor (C), combines both sides, and creates a new merge commit with two parents. No existing commit is altered. The history records exactly what happened: two lines of work that joined.

  • History: non-linear, with a branch-and-join shape.
  • Commits: E and F keep their original hashes and timestamps.
  • Conflicts: resolved once, in the merge commit.
  • Fast-forward: if main has not moved, git just slides the pointer forward and creates no merge commit (use --no-ff to force one).

git rebase

git switch feature
git rebase main

Git takes the commits unique to feature (E, F), sets them aside, moves the branch base to the tip of main (D), and replays each commit on top. Each replayed commit has a different parent, so it gets a new hash: E′, F′. The originals become unreachable (still recoverable via git reflog for a while).

Now feature is a straight line on top of main. To finish, merge it into main; that is a clean fast-forward:

git switch main
git merge feature   # fast-forward, no merge commit
  • History: linear, as if you had started your work after D.
  • Commits: new hashes (and new committer timestamps); contents may differ if conflicts were resolved.
  • Conflicts: may need to be resolved once per replayed commit.
  • Interactive: git rebase -i lets you squash, reorder, edit, or drop commits.

The golden rule

Never rebase commits that others have already pulled. Rebasing changes commit hashes. If teammates built work on the old commits, their history and yours now disagree, which leads to duplicated commits and painful reconciliation. Pushing a rebased branch needs git push --force-with-lease, so only do that on branches that are yours alone.

Which should I use?

Reach for merge when…

  • The branch is shared or public.
  • You want an exact record of how work was integrated.
  • You are bringing a finished feature into main and want a visible join point.

Reach for rebase when…

  • Updating your private feature branch with the latest main.
  • Cleaning up local commits before opening a pull request.
  • Your team prefers a linear history.

A common workflow combines them: rebase locally to stay current and tidy, then merge (or fast-forward) to integrate.
